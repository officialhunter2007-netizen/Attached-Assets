الفكرة الكاملة: معمارية "الشرح البصري الموحّد" للإنتاج
المبدأ الحاكم: استدعاء واحد، عقد بيانات صارم، عرض حتمي، وفشل غير مرئي. النص والرسم يولدان من عقل واحد في لحظة واحدة، والكود المحلي يتحمل كل مسؤولية الرسم، وأي فشل في أي طبقة يجب ألا يراه الطالب أبداً.

1. الاستدعاء الموحّد (بدل الاستدعاءين المتوازيين)
استدعاء واحد لـ Claude يستخدم Tool Use بأداة معرّفة اسمها render_visual، مع streaming للنص:

الـ system prompt يشرح للنموذج: "أنت معلم تقني. اشرح نصياً دائماً. إذا كان الموضوع يستفيد من رسم تفاعلي، استدعِ أداة render_visual بعد الشرح". 
النموذج يبث النص أولاً (الطالب يراه فوراً stream)، ثم إن قرر، يستدعي الأداة بـ JSON مطابق للـ schema.
لماذا هذا جوهري: تختفي 4 مشاكل دفعة واحدة: كشف النية بالـ regex (النموذج نفسه يقرر)، اختيار النوع بالـ keywords (حقل type في الأداة)، تضارب النص مع الرسم (مصدر واحد)، وفشل JSON.parse (الـ API يضمن بنية الأداة).
الـ regex يبقى لكن بدور معكوس: موجّه سياق فقط. إذا طابق السؤال pattern تقني، نضيف سطراً للـ prompt: "هذا السؤال مرشح قوي لرسم بصري". تلميح، ليس قراراً.

التكلفة: استدعاء واحد بدل اثنين = توفير ~40% من التكلفة مع اتساق مضمون. زمن الرسم يتأخر ثواني عن النص، وهذا مقبول لأن الطالب مشغول بقراءة النص المتدفق.

2. عقد البيانات (Schema) بإصدارات
الـ schema هو قلب النظام، ويجب أن يكون مُصدَّراً (versioned):



{
  "schema_version": "1.0",
  "type": "sequence | stepper | comparison | none",
  "theme": "security | networking | algorithm | general",
  "title": "string (≤ 60 حرف)",
  "payload": { ... حسب النوع ... }
}

قيود صارمة داخل تعريف الأداة نفسها (ليس في الكود فقط):

sequence: entities بحد أقصى 5 (maxItems في الـ schema)، steps بحد أقصى 12، نص الرسالة ≤ 40 حرفاً، الـ description ≤ 400 حرف.
stepper: خطوات 3-10، لكل خطوة title, explanation, affected[], status.
comparison (النوع الثالث الجديد): axes[] (محاور المقارنة) وitems[] (2-3 عناصر)، لأن أسئلة "الفرق بين X وY" هي الأكثر شيوعاً.

بعد استلام الأداة، طبقة تحقق مزدوجة بـ Zod: البنية + القواعد الدلالية (كل from/to في steps يشير لـ entity موجود فعلاً، لا خطوة بلا شرح). أي فشل = type: "none" + تسجيل الحادثة، والطالب يرى النص فقط.
قيّد المشاكل عند المصدر: الـ prompt يقول صراحة "إن احتاج الموضوع أكثر من 5 أطراف، ادمج الثانوية في طرف واحد باسم جامع".

3. طبقة العرض: Renderer Registry



renderVisual(data, container)
    └── registry[data.type] → SequenceRenderer | StepperRenderer | ComparisonRenderer

كل renderer وحدة مستقلة بواجهة موحدة: render(payload, el), destroy(), goToStep(n). هذا يعني إضافة نوع رسم رابع مستقبلاً = ملف جديد + سطر تسجيل، بدون لمس الموجود.
قواعد إلزامية لكل الـ renderers:

لا innerHTML أبداً مع أي نص قادم من الـ JSON. فقط textContent وcreateElement. هذا يغلق باب XSS نهائياً لأن مدخلات الطالب تمر عبر النموذج للـ JSON.
احتفظ بحيلة الـ opacity في الـ sequence، فهي صحيحة.
إمكانية الوصول: نص شرح الخطوة داخل aria-live="polite"، أزرار التنقل عناصر <button> حقيقية، دعم مفاتيح ← → للتنقل، وprefers-reduced-motion يعطل الـ transitions.
responsive: الـ viewBox ثابت لكن الحاوية max-width: 100% مع overflow-x: auto للموبايل، لأن نسبة كبيرة من الطلاب سيستخدمون هواتفهم.
كل renderer يستقبل الحالة (الخطوة الحالية) ويحفظها، بحيث إعادة الـ React re-render لا تفقد موضع الطالب: خزّن currentStep في state الرسالة نفسها لا في الـ DOM.


4. التخزين المؤقت (Caching) - أهم عنصر للحجم الذي تذكره
مع آلاف الطلاب يومياً، ستتكرر الأسئلة الجوهرية ("كيف يعمل TLS handshake") مئات المرات. طبقتان:

cache تحريري (منسّق): للمواضيع الأساسية في مناهجك (أنت تعرفها مسبقاً: TCP، TLS، NTLM، خوارزميات الترتيب...) أنشئ visual JSONs مراجعة يدوياً ومخزنة كملفات ثابتة. عند تطابق السؤال معها دلالياً، قدّمها فوراً بدون API. هذه هي "الجودة المضمونة" التي يعتمد عليها الطلاب يومياً، لأن أفضل رسم للـ handshake هو الذي راجعه معلم بشري مرة واحدة.
cache ديناميكي: للأسئلة المولّدة، خزّن الـ JSON الناجح (بعد التحقق) بمفتاح = hash للسؤال المطبَّع + schema_version. مدة صلاحية أسبوع. عند تغيير الـ schema version يبطل الـ cache تلقائياً.

هذا يحوّل التكلفة من خطية مع عدد الطلاب إلى شبه ثابتة مع عدد المواضيع.

5. الموثوقية والفشل الرشيق
سلسلة الدفاع، بالترتيب:

فشل استدعاء الأداة أو timeout (> 15 ثانية للرسم) ← النص وحده يُعرض، بلا أي مؤشر خطأ.
فشل التحقق بـ Zod ← نفس الشيء + حدث visual_validation_failed يُسجَّل مع الـ payload الفاشل (هذا كنزك لتحسين الـ prompt لاحقاً).
خطأ runtime داخل renderer ← غلّف render() بـ try/catch يزيل الحاوية بصمت. رسم مكسور نصفياً أسوأ من لا رسم.
زر "أبلغ عن مشكلة في الرسم" صغير أسفل كل رسم: الطلاب هم أفضل QA لديك، والبلاغ يرسل السؤال + الـ JSON للمراجعة.

القاعدة: الرسم ميزة تعزيزية (progressive enhancement)، النص هو المنتج. لا يجوز أن يمنع فشلُ الرسم الدرسَ أبداً.

6. القياس والتحسين المستمر (Observability)
بدون قياس لن تعرف إن كانت الميزة تعمل فعلاً. سجّل لكل رسالة:

هل استدعى النموذج الأداة؟ أي نوع؟ نجح التحقق؟
مقياس التفاعل الحاسم: هل ضغط الطالب "التالي"؟ كم خطوة أكمل؟ رسم لا يتفاعل معه أحد بعد الخطوة الأولى = ضجيج بصري يجب مراجعة متى يظهر.
زمن توليد الرسم، معدل الفشل لكل نوع، معدل البلاغات.

لوحة أسبوعية بسيطة بهذه الأرقام تخبرك أين تحسّن الـ prompt وأي مواضيع تستحق ترقية لـ cache التحريري.

7. التدفق النهائي الكامل



سؤال الطالب
    ↓
تطبيع السؤال → فحص cache (تحريري ثم ديناميكي)
    ↓ (miss)
regex hint (اختياري) يُضاف للـ prompt
    ↓
استدعاء Claude واحد (streaming + tool: render_visual)
    ↓
النص يتدفق فوراً لفقاعة الدردشة
    ↓ (إن استُدعيت الأداة)
Zod validation (بنية + دلالة)
    ├── فشل → type:"none" + log
    └── نجاح → حفظ في cache → setMessages({text, visualData})
    ↓
Renderer Registry → render آمن (textContent فقط)
    ↓
تتبع تفاعل الطالب (خطوات، إكمال، بلاغات)
