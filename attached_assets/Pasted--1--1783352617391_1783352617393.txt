# ميزة الشرح البصري التفاعلي — عرض تقني لفريق التطوير

## 1. الفكرة العامة

بدل ما نعتمد على شرح نصي فقط لمواضيع تقنية متسلسلة (بروتوكولات شبكات، هجمات أمنية، خوارزميات)، نضيف طبقة تولّد **مخططات تسلسلية تفاعلية (Interactive Sequence Diagrams)** مبنية من مخرجات الـ LLM نفسه، ويتم عرضها خطوة بخطوة مع تحريك بصري بسيط (حزمة بيانات تتحرك، سهم يظهر، لون يتغير).

الهدف: تحويل شرح مثل "TCP three-way handshake" أو "NTLM Relay Attack" من فقرة نصية إلى تجربة يشاهد فيها الطالب كل خطوة تحصل بين الأطراف (Client/Server/Attacker) بالتسلسل الزمني الصحيح.

## 2. لماذا هذا الأسلوب تحديدًا (وليس فيديو أو صور جاهزة)؟

| الخيار | المشكلة |
|---|---|
| فيديو مُنتج مسبقًا | لا يغطي كل الأسئلة الديناميكية، تكلفة إنتاج عالية، لا يتناسب مع دردشة تفاعلية |
| صورة يولدها نموذج (DALL-E/SD) | غير دقيقة تقنيًا، النصوص داخل الصورة غالبًا مشوهة، لا يمكن التحكم بالتسلسل |
| رسم يدوي ثابت لكل موضوع | يعمل لعدد محدود من المواضيع فقط، لا يتوسع مع تنوع الأسئلة |
| **مخطط منظم (JSON) + رندر من الواجهة** | **الأدق: النموذج يوصف "ماذا يحدث"، والواجهة تتحكم بـ"كيف يظهر"** |

الاختيار الأخير هو الأنسب لأنه يفصل بين المسؤوليات: النموذج مسؤول عن المحتوى التقني الصحيح، والفرونت إند مسؤول عن الشكل والحركة.

## 3. الهيكلية التقنية المقترحة (Architecture)

```
[سؤال المستخدم]
      ↓
[Prompt خاص يطلب من LLM إرجاع JSON منظم بدل نص حر]
      ↓
[Backend يتحقق من صحة الـ JSON (schema validation)]
      ↓
[Frontend Component مخصص يقرأ الـ JSON ويرسم Sequence Diagram متحرك]
      ↓
[عرض تفاعلي: خطوة بخطوة + شرح نصي مرافق]
```

### 3.1 تنسيق البيانات (Schema)

نطلب من النموذج أن يرجع بيانات بصيغة موحدة، مثال لـ TCP handshake:

```json
{
  "title": "TCP Three-Way Handshake",
  "actors": ["Client", "Server"],
  "steps": [
    {
      "from": "Client",
      "to": "Server",
      "label": "SYN",
      "explanation": "العميل يطلب بدء الاتصال ويرسل رقم تسلسل عشوائي"
    },
    {
      "from": "Server",
      "to": "Client",
      "label": "SYN-ACK",
      "explanation": "الخادم يوافق ويؤكد استلام الطلب"
    },
    {
      "from": "Client",
      "to": "Server",
      "label": "ACK",
      "explanation": "العميل يؤكد، والاتصال أصبح مفتوحًا"
    }
  ]
}
```

نفس الفكرة تنطبق على NTLM Relay لكن مع إضافة طرف ثالث (Attacker) ولون مختلف يوضح أنه غير شرعي:

```json
{
  "title": "NTLM Relay Attack",
  "actors": ["Victim", "Attacker", "Target Server"],
  "steps": [
    {"from": "Victim", "to": "Attacker", "label": "NTLM Auth Request", "type": "normal"},
    {"from": "Attacker", "to": "Target Server", "label": "Relay Auth", "type": "malicious"},
    {"from": "Target Server", "to": "Attacker", "label": "Challenge", "type": "normal"},
    {"from": "Attacker", "to": "Victim", "label": "Forward Challenge", "type": "malicious"}
  ]
}
```

حقل `"type"` يسمح للواجهة تلوين الأسهم (أحمر للخبيث، أزرق للطبيعي) بدون ما يحتاج النموذج يهتم بالألوان.

### 3.2 مكونات الفرونت إند

- **مكتبة الرسم**: نبدأ بـ Mermaid.js (خفيفة، تدعم sequence diagrams جاهزة) أو نبني Component مخصص بـ React/SVG لو أردنا تحكم أكبر بالحركة والألوان.
- **Player Control**: أزرار "التالي / السابق / تشغيل تلقائي" لعرض الخطوات بالتسلسل، مع شريط تقدم.
- **Sync بين المخطط والشرح**: كل خطوة تسلط الضوء على السهم المعني في المخطط + تعرض شرحها النصي أسفله في نفس الوقت.
- **الألوان حسب الدور**: تلقائيًا نربط كل Actor بلون ثابت (Client=أزرق، Server=أخضر، Attacker=أحمر) بناءً على الاسم أو حقل type.

### 3.3 الباك إند

- **Prompt Engineering**: نضيف System Prompt يوجه النموذج لإرجاع الـ JSON بالصيغة المتفق عليها فقط عندما يكتشف أن السؤال "تسلسلي" (بروتوكول، هجوم، خوارزمية بها خطوات).
- **Function/Tool Calling**: لو المنصة تستخدم نموذج يدعم tool calling، نجعل توليد الرسم البياني عبارة عن "أداة" يستدعيها النموذج بدل تضمينه بالنص العادي، وهذا يقلل أخطاء تنسيق الـ JSON.
- **Validation Layer**: قبل إرسال الـ JSON للواجهة، نتحقق من الـ schema (باستخدام Zod أو Pydantic) ونرفض/نعيد الطلب لو فيه خلل بالتنسيق.

## 4. مراحل التنفيذ المقترحة

1. **مرحلة أولى (MVP)**: دعم Mermaid.js مباشرة — النموذج يولد كود Mermaid نصي، نعرضه فورًا بدون أنيميشن معقد. تنفيذ سريع، يثبت الفكرة.
2. **مرحلة ثانية**: الانتقال لصيغة JSON المخصصة + Component مبني داخليًا يدعم العرض خطوة بخطوة والألوان حسب الدور.
3. **مرحلة ثالثة**: إضافة تفاعلية أعمق — مثل "خمّن الخطوة القادمة" قبل عرضها، أو السماح للمستخدم يبدل معطى (مثال: تغيير رقم البورت) ومشاهدة تأثيره على التسلسل.
4. **مرحلة رابعة (اختيارية)**: لمواضيع أساسية متكررة (TCP handshake, DNS resolution, TLS handshake...) إنتاج أنيميشن احترافي جاهز مسبقًا (بأدوات مثل Manim) لعرضه بدل التوليد الحي، توفيرًا للوقت والتكلفة.

## 5. نقاط يجب مناقشتها مع الفريق

- هل نعتمد على Function Calling من النموذج لإجبار صيغة الإخراج، أم Prompt عادي مع Regex/Parsing كخط دفاع أول؟
- هل نبني مكتبة الرسم داخليًا أم نعتمد على Mermaid/D3.js كنقطة انطلاق؟
- كيف نتعامل مع الأخطاء لو النموذج أرجع JSON غير صالح؟ (إعادة المحاولة تلقائيًا أم fallback لشرح نصي عادي؟)
- هل نحتاج Caching للمخططات الشائعة (نفس السؤال بالضبط) لتقليل تكلفة استدعاء النموذج؟

## 6. الخلاصة

الميزة قابلة للتنفيذ بمراحل تدريجية، تبدأ بسيطة (Mermaid) وتتوسع لتجربة تفاعلية غنية. أهم قرار تقني هو **فصل مسؤولية التوليد (محتوى تقني من النموذج) عن مسؤولية العرض (رسم وحركة من الفرونت إند)** عبر تنسيق JSON موحد، لأنه يعطي أعلى دقة وأقل أخطاء بصرية مقارنة بمحاولة جعل النموذج "يرسم" مباشرة.
